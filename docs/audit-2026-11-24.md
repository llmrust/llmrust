### 1.3 核心调用链

#### 非流 Chat

1. [`LmrsClient::chat_with`](src/lib.rs#L461-L481) 解析 `provider/model`。
2. 从共享 `Arc<RwLock<HashMap>>` 获取 Provider。
3. 覆盖 `req.model`，执行 CAP-003 能力裁决。
4. 调 `Provider::chat`；Provider 构造 wire JSON、发送 HTTP、解析响应。
5. 返回 `ChatResponse`；代理非流路径再转成目标协议 JSON。

#### 流式 Chat

1. [`LmrsClient::stream_with`](src/lib.rs#L495-L521) 解析模型、设置 `stream=true`、执行能力裁决。
2. Provider 建立 HTTP 响应并返回字节/事件流。
3. Provider 解析 SSE/NDJSON，重组工具与 thinking。
4. 公共边界套 [`unify_terminal`](src/providers/stream_state.rs#L176-L190)，延迟并合并 terminal。
5. `stream_collect*` 拼接文本；遇到 reasoning 返回 Unsupported。

#### Embedding

1. [`LmrsClient::embed_with`](src/lib.rs#L619-L634) 解析模型并剥离 provider 前缀。
2. OpenAI-compatible 发 `/embeddings`；Ollama 发 `/api/embed`。
3. 不支持者依赖 `Provider::embed` 默认 Unsupported。
4. RetryProvider 委派 embedding；Router **不**路由 embedding。

#### 代理

- OpenAI Chat 与 Embeddings、Anthropic Messages、OpenAI Responses 共用 `AppState` 和 provider 注册表。
- 非流路径走 `LmrsClient::chat_with`，因此有统一能力裁决。
- **三个流式 handler 直接 `get_provider().stream()`**，绕过统一裁决与 terminal 归一化，这是 P1-04 的根因。

### 1.5 工程质量基线

做得较好的方面：

- `default=[]`，Axum 等服务器依赖只在 `proxy` feature 启用。
- Provider trait 要求 chat/stream，embed 默认 Unsupported；wrapper 委派关系清楚。
- reqwest Client 复用，hosted 120s 总超时、30s connect timeout、keepalive、连接池。
- Google key 走 `x-goog-api-key` header；Anthropic 走 `x-api-key`。
- `ProviderConfig` Debug 掩码 key、base URL、自定义 header。
- 行重组正确处理合法 UTF-8 跨 packet、CRLF 和多行尾块。
- Bearer 使用 `subtle::ConstantTimeEq`；无 key 时禁止非 loopback 绑定。
- 4xx/429 不同部署重试策略区分清楚；流中途错误不重试。
- CI action SHA 固定，release 使用 OIDC；semver、package、架构守卫意识强。

## 4. P1 / High：下一版前应阻断处理

> 分级口径：P1 = 可造成数据/凭证泄露、错误结果被当成功、明确核心契约失效，或直接阻断安全/发布门。未确认 P0。

### P1-02 reqwest 错误携带完整 URL，URL 凭证进入公开错误

**状态：运行时复现。**

- [`LlmError::Http`](src/providers/mod.rs#L27-L28) 直接包装 reqwest Error。
- compat 在 [`src/providers/compat.rs:770-780`](src/providers/compat.rs#L770-L780) 与 [`src/providers/compat.rs:815-825`](src/providers/compat.rs#L815-L825) 用 `?` 原样上传。
- 本地探针使用 `http://127.0.0.1:1/v1?token=AUDIT_SECRET`，错误文本同时包含 secret 与完整 URL。
- OpenAI/Anthropic SSE 错误直接 `e.to_string()`；Responses 非流错误也直接 `e.to_string()`，见 [`src/proxy/mod.rs:1027-1041`](src/proxy/mod.rs#L1027-L1041)、[`src/proxy/anthropic_proxy.rs:888-902`](src/proxy/anthropic_proxy.rs#L888-L902)、[`src/proxy/responses_proxy.rs:950-963`](src/proxy/responses_proxy.rs#L950-L963)。

**影响**：凭证可进入调用方日志、错误监控，甚至代理客户端响应。`ProviderConfig` Debug 掩码无法保护此路径。

**修复**：Provider 边界对 reqwest error 调 `without_url()`；拒绝/规范化含 userinfo、query secret 的 base URL；代理 SSE 对 Http 使用固定安全消息。

### P1-03 跨源 307/308 重定向重放 POST 正文和自定义敏感 header

**状态：运行时复现。**

- [`build_http_client`](src/providers/http.rs#L42-L46) 未设置 redirect policy，使用 reqwest 默认跟随策略。
- 自定义 header 被装进 client 默认 headers，见 [`src/providers/http.rs:50-70`](src/providers/http.rs#L50-L70)。
- 本地第一个 HTTP 服务返回跨源 307，第二个服务捕获到完整 `redirect-prompt` 与 `x-api-key: REDIRECT_SECRET`。
- 标准 `Authorization` 会被 reqwest 剥离，但任意 `x-api-key` 等非标准敏感 header 不会；Anthropic 的 `x-api-key` 与 Google 的 `x-goog-api-key` 也属于此类。

**影响**：上游被攻破或错误重定向时，prompt、工具参数、图片、embedding input、自定义密钥以及 Anthropic/Google 原生 API key 可被重放到另一主机。

**修复**：凭证请求默认 `Policy::none()` 或仅同源；跨源重显 opt-in；禁止跨源 307/308 重放 body；补重定向安全测试。

### P1-04 三个代理流式 handler 绕过能力裁决与流终态归一化

**状态：静态确认。**

- OpenAI Chat：[`src/proxy/mod.rs:1078-1083`](src/proxy/mod.rs#L1078-L1083)
- Anthropic：[`src/proxy/anthropic_proxy.rs:1018-1025`](src/proxy/anthropic_proxy.rs#L1018-L1025)
- Responses：[`src/proxy/responses_proxy.rs:927-935`](src/proxy/responses_proxy.rs#L927-L935)

三处都是 `get_provider()` 后直接 `provider.stream()`；非流路径却走 `LmrsClient::chat_with`。

**影响**：

- 流式 Ollama tools/image 不会像非流一样被 CAP-003 拒绝；Ollama 请求体不发送 tools，图片被扁平化，形成静默能力丢弃。
- DeepSeek/Moonshot 等图片能力差异在流式代理被绕过。
- Provider 原始流不经过 `unify_terminal`，terminal、post-terminal 元数据和错误优先级由三套代理各自处理，直接导致 P1-05/P1-06 与 P2 多项漂移。

**修复**：抽出共享 raw-stream dispatch，完成 model 解析、provider 获取和 adjudication；再明确由哪一层负责 terminal/truncation，不能各协议私自定义。

### P1-05 Responses 端点会丢 reasoning、丢请求语义并把截断标成 completed

**状态：静态确认，多个子缺陷同属一个协议边界。**

1. **reasoning 请求被接受但流式 thinking 被忽略**
   - 任意非 `none/disabled` effort 都映射为固定 `medium`，见 [`src/proxy/responses_proxy.rs:361-369`](src/proxy/responses_proxy.rs#L361-L369)。
   - SSE 主循环不处理 `thinking/thinking_done`，却在 usage 中输出 reasoning tokens，见 [`src/proxy/responses_proxy.rs:621-711`](src/proxy/responses_proxy.rs#L621-L711)、[`src/proxy/responses_proxy.rs:831-843`](src/proxy/responses_proxy.rs#L831-L843)。
   - `low/high` 被降级成 `medium`；`none` 无法保证关闭模型默认 reasoning。

   - `emit_completed` 固定 `status:"completed"`，见 [`src/proxy/responses_proxy.rs:844-854`](src/proxy/responses_proxy.rs#L844-L854)。

3. **finish reason 完全不影响 Responses status**

4. **请求字段静默丢弃/误解**

   - 未知 content part 仅 warn 后跳过，见 [`src/proxy/responses_proxy.rs:393-395`](src/proxy/responses_proxy.rs#L393-L395)。

5. **错误状态映射错误**
   - Unsupported、Parse、Http 都落到 502 `upstream_error`，见 [`src/proxy/responses_proxy.rs:950-963`](src/proxy/responses_proxy.rs#L950-L963)；Unsupported 应是 400 客户端错误。

**影响**：Responses 客户端可能把思考丢失、参数约束失效、会话延续失效、截断/过滤输出当作完整成功，进而触发错误业务动作。

**修复**：逐字段实现或显式 400 拒绝；EOF 检查 `done_seen`；映射 finish reason 到 `completed/incomplete/failed`；thinking 无法忠实表达时失败而不是静默继续。

### P1-06 OpenAI Chat 代理 SSE 缺工具 index，且 finish reason 被编造或跨协议非法映射

**状态：静态确认。**

- [`ProxyDelta.tool_calls`](src/proxy/mod.rs#L268-L276) 直接使用 `Vec<ToolCall>`；共享 [`ToolCall`](src/types.rs#L103-L118) 没有 `index`。
- SSE 在 [`src/proxy/mod.rs:995-1003`](src/proxy/mod.rs#L995-L1003) 一次性序列化完整 ToolCall，没有稳定 index。
- 流式 finish 缺失时合成 ToolCalls/Stop，见 [`src/proxy/mod.rs:959-967`](src/proxy/mod.rs#L959-L967)；非流同样合成，见 [`src/proxy/mod.rs:777-786`](src/proxy/mod.rs#L777-L786)。
- 跨协议直接 `FinishReason::as_str()`：Anthropic `end_turn/max_tokens/tool_use/stop_sequence` 会原样进入 OpenAI wire，而这些不是 OpenAI 合法 finish 值。

**影响**：严格 OpenAI SDK 可能无法重组工具调用；缺失原因被伪装成正常结束；Anthropic/Gemini 后端经 Chat 代理输出不符合目标 schema。

**修复**：使用专用 `ProxyToolCallDelta { index, id?, name?, arguments? }`；为每个目标协议实现 finish 映射；缺失保持 null，不合成 Stop。

### P1-07 流字节管线无界、有损且不是完整 SSE 解析

**状态：静态确认 + 运行时复现非法 UTF-8。**

- [`line_stream`](src/providers/stream_util.rs#L37-L68) 在遇到换行前持续 `buf.extend_from_slice`，没有最大行/事件上限。
- 每次新 chunk 从 buffer 起点找 `\n`，超长单行可形成近似 O(n²) CPU。
- 完整行与 EOF tail 使用 `String::from_utf8_lossy`，见 [`src/providers/stream_util.rs#L48`](src/providers/stream_util.rs#L48) 与 [`src/providers/stream_util.rs#L58`](src/providers/stream_util.rs#L58)；探针确认非法字节被替换为 U+FFFD 且返回 Ok。
- Anthropic/Google/compat 只识别严格 `data: ` 前缀，不支持 `data:{...}`、多行 data、仅 CR、BOM、标准 event dispatch。
- HTTP 200 非 SSE 内容可能被逐行忽略，最后合成空成功。

**影响**：恶意/故障上游可导致 OOM 或 CPU 放大；非法 UTF-8 被静默改写；合法 SSE 变体被丢数据。

**修复**：实现有界标准 SSE 事件解析器；严格 UTF-8，失败返回 Parse/Stream；限制行、事件、工具参数、响应体大小；200 非 SSE 必须报错。

#### P2-36 公共流边界静默丢弃 terminal chunk 的 reasoning

**状态：运行时复现。**

- 公开入口在 [`src/lib.rs:517-521`](src/lib.rs#L517-L521) 套 `unify_terminal`。

**修复**：保存 terminal thinking，或先拆成非 terminal reasoning chunk；补“经 `LmrsClient::stream_with` 的 terminal thinking 不丢失”端到端测试。

#### P2-37 Retry-After 不是请求级状态，embedding 重试还完全忽略 hint

**状态：静态确认 + 运行时复现 embedding 路径。**

- hint 存在 Provider 实例级 `Mutex<Option<Duration>>`，见 [`src/providers/compat.rs:648-652`](src/providers/compat.rs#L648-L652)。
- 只有非 2xx `parse_error` 写槽；成功和网络错误不清除，见 [`src/providers/compat.rs:789-803`](src/providers/compat.rs#L789-L803)。

**修复**：hint 与单次调用/错误绑定；embedding 使用 `backoff_with_hint` 并记录 `delay_source`；补并发交错、成功清除、network error 清除测试。

#### P2-38 Anthropic 工具 flush 不验证完整性，代理还会伪造 stop reason

**状态：运行时复现；clean EOF flush 本身是文档允许的，问题在完整性与下游语义。**

- 工具 start 缺 index/id/name 时回退默认值，见 [`src/providers/anthropic.rs:719-727`](src/providers/anthropic.rs#L719-L727)。
- 参数只拼接字符串，不验证最终 JSON，见 [`src/providers/anthropic.rs:636-681`](src/providers/anthropic.rs#L636-L681)。
- `message_delta` 不检查 `content_block_stop` 就 `tools.take()`，见 [`src/providers/anthropic.rs:777-793`](src/providers/anthropic.rs#L777-L793)。
- clean EOF flush 已由 [CONTRACTS.md](docs/CONTRACTS.md#L45) 明确允许；但 [`src/proxy/anthropic_proxy.rs:795-827`](src/proxy/anthropic_proxy.rs#L795-L827) 会把 EOF flush 的 `finish_reason=None` 洗成 `tool_use/end_turn` 并发送 `message_stop`。

**复现**：只发送工具 start 与 `partial_json:"{\"x\":"` 后 EOF，得到 `done:true`、`arguments=="{\"x\":"`、JSON 非法。

**影响**：调用方可能执行参数不完整的工具；代理进一步把“上游未给原因”伪装成正常 tool_use/end_turn。

**修复**：跟踪 block 闭合；flush 前验证 id/name 非空和 arguments 是合法 JSON；代理对 EOF flush 的缺失原因保持 null 或报 incomplete/error，不伪造正常结束。

#### P2-39 Gemini 合成工具 id 跨轮重复，旧工具结果解析到错误函数名

**状态：运行时复现。**

- 每次响应从 `call_0` 开始，见 [`src/providers/google.rs:414-425`](src/providers/google.rs#L414-L425)、[`src/providers/google.rs:1047-1054`](src/providers/google.rs#L1047-L1054)。

- 工具结果按该全局映射解析 name，见 [`src/providers/google.rs:631-650`](src/providers/google.rs#L631-L650)。

**复现**：第一轮 `call_0=first_tool`，第二轮 `call_0=second_tool`；两个 functionResponse 都变成 `second_tool`。

**影响**：工具执行上下文被污染，模型收到错误函数结果。

**修复**：响应级唯一 id；按最近未匹配 assistant call 的轮次作用域解析；优先使用 `Message::tool.name`；补两轮重复 id 回归测试。

#### P2-40 Gemini HTTP 200 空 candidates / 安全阻止被转换成 `Ok("")`

**状态：运行时复现。**

- 非流 `GeminiResponse` 不建模 `promptFeedback`，见 [`src/providers/google.rs:221-229`](src/providers/google.rs#L221-L229)。

**复现**：HTTP 200 `{"promptFeedback":{"blockReason":"SAFETY"}}` 返回 `Ok` 且 `content==""`。

**影响**：安全拒绝/上游错误与正常空输出无法区分，违反“错误不得返回空成功”。

**修复**：非流建模 promptFeedback；blockReason 返回明确错误；无 candidates 且无合法解释时返回 Parse/Stream。

#### P2-41 E2E smoke 对真实失败仍返回成功

**状态：静态确认。**

- [`examples/e2e_smoke.rs:475-501`](examples/e2e_smoke.rs#L475-L501) 收集任务输出后直接打印；`JoinError` 被忽略，没有失败计数或 `process::exit(1)`。

- stream path 只读首帧，tools path 不要求真实 tool call；后续流错误或空工具结果也可能假绿。

**影响**：真实协议漂移、401、500、parse 错误、panic 都可留下绿色 smoke；该脚本更接近诊断打印器，不是发布门。

**修复**：累计 path failure 与 JoinError，严格模式非零退出；消费完整 stream 并断言 terminal/tool_calls/thinking；要求最小 provider 覆盖。

## 8. 测试体系审计：为什么 593 个测试全绿仍有 P1

### 8.1 覆盖较好的部分

- 响应 JSON shape freeze 负例扎实。
- CAP-004 对 provider 矩阵、JSON、有限运行时能力面有一致性检查。
- 架构边、热点台账、package、guard admission 有负例意识。
- SSE 合法分片、CRLF、UTF-8 跨 packet、delta:null、tool index 上界、错误不 flush 等局部测试有效。
- Router 的基础 failover、cooldown、per-group RR 有覆盖。
- Proxy 的 n、认证、body limit、reasoning 拒绝、基础 SSE 有覆盖。

### 8.2 系统性盲区

1. **元数据自证**：API freeze 主要校验 JSON 清单，不校验真实 Rust API；CAP-004 不覆盖 sampling/image/response_format/cache 的完整语义。
2. **测试内重写生产逻辑**：部分 Anthropic/Gemini 文本拼接、工具转换、usage 转换在测试里手工实现，生产函数坏了仍可绿。
3. **缺生产 wire fixture**：Anthropic/Gemini chat/stream 没有完整本地 HTTP 契约测试；compat 的 HTTP 测试还借 `proxy` feature。
4. **生命周期测试断层**：provider 局部解析测试与 `LmrsClient`/Proxy 公共流测试分离，terminal thinking、错误后 done、EOF 截断、慢 EOF 未贯通。
5. **日志不可观测**：没有 scoped tracing subscriber；warn-once、delay_source、敏感信息禁令主要靠字符串扫描。
6. **并发缺失**：Retry-After 共享槽、cooldown 并发、重复 with_retry 无测试。
7. **E2E 不构成门**：错误 exit 0、stream 只读首帧、tools 不要求 tool call、零 secret 也成功。
8. **守护门可绕过**：guard admission 不验证测试属性；architecture/hygiene 是文本扫描；必需治理文档读取失败可跳过。

## 12. 最终裁定

- **功能正确性**：主路径可用，但流式、工具、reasoning、Responses 与错误边界存在多项确定性缺陷，不能据 593 个通过测试判定“契约全部成立”。
- **安全**：认证常量时间、默认 loopback、key header 等基础控制良好；reqwest URL 错误和跨源重定向是真实凭证/正文泄露路径。
- **架构**：Provider trait、共享 compat、Router/Retry 分离方向正确；主要结构债是流式状态机跨层分裂、能力声明与最终 wire 脱节、types→cache→Anthropic 间接耦合。
- **测试**：数量多、负例意识强，但元数据自证、生产 wire fixture 缺失和生命周期断层使绿灯置信度有限。
- **治理**：历史 RC-0.1.3/0.1.4 的 GO 只对各自 commit 有效；当前 main 缺后继 SSOT、延期债务承接和发布/开发版本关系说明，不能沿用历史 GO。
- **发布**：本地构建全绿、相邻版本 semver 全绿；但 cargo-deny 公告红、包内含 207 个内部文件、tag 发布缺完整质量门，当前应判定 **NO-GO until P1-13～P1-15 closed**；E2E 的 P2-41 在修复前也不能作为发布证据。
