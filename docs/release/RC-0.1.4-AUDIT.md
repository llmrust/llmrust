## 7. ⑦ §1.5 递归改进三问——覆盖率核验（**阻断项**）

**要求**（`RC-002` DoD 原文）："**核验 §1.5 三问在每张已合并卡的 PR 中均有回答**"、"三问覆盖率 100%"。

**实测**（逐 PR 读取 PR body，只读 API）：

| 指标 | 数 |
|---|---|
| 本版范围相关的**已合并 PR 总数** | **25** |
| 其中 PR body **完整含三问**（机制问 + 门禁问 + 同族问） | **3**（`#206`、`#208`、`#215`） |
| **缺失** | **22** |
| **覆盖率** | **3/25 = 12%** ❌ |

**补充排查（排除"写在别处"）**：
- **PR 评论**：抽查 #226–#231，**均无**三问内容（`comments` 为空或无关）；
- **提交信息**：main 最近 16 笔**全部**不含三问（`机制问`/`同族问` 零命中）。

**结论**：**§1.5 三问覆盖率 `12%`，远未达 100%** ⇒ **`RC-002` 的 DoD 未满足**。
这 22 张里**包含今天全部 `CAP-002..007` 与 `ERR-001..005`**（即本次 `N1`/`N2` 的主体工作）。

**为什么这不是"形式主义"**：§1.5 三问的**目的是强制"修机制而非修实例"**——
它要求作者回答"这个缺陷的**机制性**根因是什么、我加的门是什么、同族还有谁"。
**本版的实际执行中，机制性思维是存在的**（例：`CAP-003` 把"未声明"与"声明为 unsupported"分开而非打补丁；
`ERR-002` 把截断移出 `match` 使它成为结构性保证；`ERR-005` 消除的是一**类**而非一处），
**但这些推理没有被写进 PR**——**"做了"与"留下了可审的记录"是两件事**，而 §1.5 要求的是后者。
