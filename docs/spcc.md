> 

# 一、定位与适用范围

- SPCC 是一套**裁决驱动、证据优先、小步关账**的开发协作规范，适用于「产品 Owner 不写码 + 架构师把关 + 执行侧写码」的三角协作模式。
- 核心目标：让不懂技术的 Owner 也能通过流程约束获得可信的工程质量；让每一次合并都有完整证据链可回溯。
- 本文档只定义**规则**。项目专属内容（任务清单、缺陷地图、看板）放在各项目自己的 SSOT 页面。

# 二、角色与权责

| 角色 | 权责 | 禁止事项 |
| --- | --- | --- |
| **Owner（产品）** | 定目标与优先级；授权架构师全权裁决 | 不介入技术裁决细节 |
| **架构师** | 下发任务令；裁决设计小样与实现 PR；下合并令；维护台账；违规入档 | 不代替执行侧写码；不基于二手信息裁决 |
| **执行侧** | 按核准设计写码；报审；返修；关账回证 | **严禁自行合并**；严禁超预算/偏离设计后继续推进 |
- 争议裁决权归架构师，**不上抛给 Owner**。Owner 只在目标与优先级层面表态。
- 执行侧的 PR 永远「止步于报审」，合并令只能由架构师下发。

# 三、核心原则

1. **第一手证据原则**：任何裁决必须基于第一手直读——PR diff、issue 原文、CI run 回证、命令输出。摘要、转述、聊天复述一律视为二手信息，不得作为裁决依据。
2. **单一事实源（SSOT）**：项目规则、任务状态、裁决记录各有唯一权威页面。出现口径冲突时以 SSOT 为准，先修 SSOT 再继续。
3. **小步快审**：任务拆到单 PR 可审的粒度；每个 PR 设行数预算上限（建议 ≤400 行，功能/测试/其他三分解）。
4. **设计先行**：任何写码前必须有核准的设计小样。未经核准的形状差异 = 偏离，push 前必报。
5. **守恒清单**：每个设计小样显式列出「本次改动**不**改变的行为/接口」，实现与关账时逐条核验。
6. **文档不许失实**：CHANGELOG、PR Summary 必须与最终实现**逐字对齐**。失实即阻塞项，与代码缺陷同级。

# 四、任务生命周期（标准流水线）

1. **任务令下发**（架构师）：范围、目标、预算、验收口径。
2. **设计小样报审**（执行侧）：见 §五。
3. **设计裁决**（架构师）：APPROVE / 需修改 / REJECT。APPROVE 后方可建分支（须指明分支名与 base commit）。
4. **写码 + 实现 PR 报审**（执行侧）：报审件要件见 §六。CI 全绿是报审前置条件，不是裁决替代品。
5. **终局裁决**（架构师）：基于合并前 head 的 PR diff 第一手直读。
6. **合并令 + 合并**：架构师下合并令后方可合并。
7. **关账**（执行侧回证 + 架构师核验）：见 §七。
8. **三方复核**：代码、文档（CHANGELOG/Summary）、台账三方一致后关账落章。

任一环节被裁「需修改」，走**窄口径返修**：只重审改动项与阻塞项，已核验合格项不重新论证。

# 五、设计小样制度

设计小样是写码前的最小充分设计，必须包含：

- **问题陈述**：要修什么，第一手证据（文件:行号、复现路径）。
- **方案形状**：关键函数/数据结构/控制流的具体形状，精确到可核验（如「末字节检测 → 向前扫描至最后换行 → 物理截断 → 追加」）。
- **测试计划**：编号化集成测试（IT-1、IT-2…），每条写明场景与断言口径。
- **预算自估**：功能/测试/其他三分解，总量对齐预算上限。
- **守恒清单**：不变的公共 API、行为语义、平台承诺。
- **上线影响表**：各平台/环境的行为差异如实申报。

裁决可附 **MUST 条款**（有条件批准，返修项随实现 PR 一并核验）与**非阻塞观察项**（不阻塞批准，但实现 PR 报审时必须落实并回证）。

# 六、报审件要件（实现 PR）

缺任一项即「要件不全」，可直接裁「需修改」：

1. **head SHA**（明确指出裁决对象是哪个 commit）。
2. **CI 全绿回证**（run 编号 + 全部 job 通过）。
3. **预算三分解表**：与 `git diff --numstat` 实测对齐（生成文件如 lockfile 不计入）。
4. **行为变更清单**：所有对外可见变更（新错误类型、超时语义、平台差异）逐条列出。
5. **与核准设计的差异声明**：零差异也要显式写「无偏离」；有差异必须逐条申请追认。
6. MUST 条款与非阻塞观察项的落实回证。

# 七、关账要件

合并后关账必须回证：

1. merge commit SHA；
2. 关联 issue 已关闭；
3. 任务分支已删除；
4. 工作区 porcelain 干净（无未跟踪残留）;
5. numstat 终值三分解与报审口径一致；
6. 三方复核：代码 = 文档 = 台账。

# 八、台账同步纪律（三处同步）

每次裁决或状态变更，**当场同步三处**，缺一即违规：

1. **裁决记录**（矫正令/任务令的裁决章节，全文入档）；
2. **任务状态列**（任务令中的 Wave/阶段状态）；
3. **看板行**（任务追踪数据库对应行：状态、裁决、PR 号、分支、备注）。

> 实战教训：台账漏同步是最高频违规（同型多次入档）。裁决写完不算完，三处同步完才算完。
> 

**看板 schema 建议**：Task（标题）、状态（未开始/阻塞/开发中/评审中/需修改/已合入）、架构师裁决（APPROVE/需修改/REJECT/待审）、规模（S/M/L）、PR 号、分支、合入 commit、备注、完成（勾选）。

# 九、裁决制度

- 裁决结论三态：**APPROVE**（可附 MUST）/ **需修改**（列 F-1、F-2… 编号阻塞项，逐项可核验）/ **REJECT**（方案推倒）。
- 裁决书必须区分「已核实合格项」与「阻塞项」，返修只针对阻塞项。
- 裁决依据只能是第一手直读；执行侧聊天自述可作线索，不可作依据。
- 终局裁决以**合并前 head** 的 diff 为准；返修后 head 变更须重报重审。

# 十、偏离与违规管理

1. **停手报裁**：预算超限、设计形状偏离、意外行为变更——发现即停手报架构师，不得自行推进。
2. **违规入档**：违规事实 + 处置写入台账，可**追认**（retroactive ratify）但一律注明「不设先例」。
3. **偏离追认**：实现期发现更优方案，允许追认，但必须显式记载 + 更新守恒清单/CHANGELOG，暗改即失实。
4. 自纠回归核准形状的修改可记录不入档，但重申：任何形状差异 push 前须报。

# 十一、测试纪律

1. **禁止同义反复测试**（tautological test）：断言不得只是实现逻辑的复读；必须断言外部可观察行为。
2. **确定性断言**：断言具体值/具体计数，不用「不报错就算过」。
3. **恢复/并发类修复必须有全链 IT**：崩溃 → 恢复 → 继续写入 → 第三方重开验证。
4. 平台相关测试用条件编译如实标注，不得让跳过的平台假装被覆盖。
5. 测试代码计入预算，单独分解列示。

# 十二、文档真实性纪律

- CHANGELOG / PR Summary / 设计文档与最终实现**逐字核对**，作为终局裁决的专项核对项。
- 常见失实形态（均有实战案例）：写了旧方案名而实现已改；声称的机制与实测行为不符；行为变更（新错误类型、超时语义）漏记。
- 失实 = 阻塞项，等同代码缺陷处理。
